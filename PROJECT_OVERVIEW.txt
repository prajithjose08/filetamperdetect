--------------------------------------------------------------------------------
  PROJECT OBJECTIVE
--------------------------------------------------------------------------------

Detect whether a file has been modified by comparing its SHA-256 cryptographic
hash against a previously saved reference hash stored in a local SQLite database.

This tool helps verify the integrity of documents, images, source code files,
and any other common file types. It is intended as an educational cybersecurity
project demonstrating how hash-based integrity checks work in practice.

--------------------------------------------------------------------------------
  DATA SOURCES & DATA STORAGE
--------------------------------------------------------------------------------

  WHERE DATA COMES FROM
  ---------------------
  - All data originates from files uploaded by the user through the browser.
  - No external datasets, APIs, or cloud services are used.
  - No data is downloaded from the internet at runtime.

  WHAT IS STORED
  --------------
  The SQLite database (instance/file_integrity.db) stores two tables:

  1. registered_files
     - id             : Auto-generated unique integer record ID
     - filename       : Original filename (sanitised with secure_filename)
     - file_size      : Size of the file in bytes at registration time
     - sha256_hash    : 64-character SHA-256 hex digest of the file content
     - registered_at  : UTC timestamp of registration

  2. verification_history
     - id             : Auto-generated unique integer history ID
     - registered_id  : Foreign key linking to the reference record (nullable
                        for UNKNOWN results where no reference exists)
     - filename       : Filename of the file that was verified
     - original_hash  : Reference SHA-256 hash at the time of verification
     - current_hash   : SHA-256 hash of the uploaded file being checked
     - file_size      : Size in bytes of the uploaded file
     - result         : One of UNCHANGED, MODIFIED, or UNKNOWN
     - verified_at    : UTC timestamp of the verification event

  WHAT IS NOT STORED
  ------------------
  - Uploaded files are NEVER stored permanently on disk.
  - Each uploaded file is written to a secure OS temporary file, hashed,
    and then immediately deleted. Only the hash and metadata are kept.
  - No user accounts, passwords, or personal data are stored.
  - No cookies or sessions contain sensitive information.

  -----------------

--------------------------------------------------------------------------------
  CRYPTOGRAPHIC ALGORITHM
--------------------------------------------------------------------------------

  Algorithm   : SHA-256 (Secure Hash Algorithm, 256-bit)
  Source      : Python built-in hashlib module (uses OpenSSL internally)
  Output      : 64-character lowercase hexadecimal string
  Properties  :
    - One-way (cannot reverse a hash back to the original file)
    - Deterministic (same file always produces the same hash)
    - Avalanche effect (a single byte change produces a completely different hash)
    - Fixed output length (always 64 hex characters regardless of file size)

  Files are read in 1 MiB chunks to support large files without loading the
  entire file into memory.

--------------------------------------------------------------------------------
  KNOWN LIMITATIONS
--------------------------------------------------------------------------------

  1. The SQLite database is stored as a plain file. Anyone with filesystem
     write access can modify the stored hashes, defeating the integrity check.
     This project does NOT provide a digitally signed or tamper-proof audit trail.

  2. SHA-256 detects whether a file changed but cannot identify which specific
     bytes or lines differ, or who made the change.

  3. File-type validation is extension-based (not deep content inspection).
     This is acceptable for a local educational tool.

  4. The application uses Flask's built-in development server. For any real
     deployment, a production WSGI server (e.g. gunicorn, waitress) should be
     used instead.

  5. This application is designed for local, single-user educational use.
     It does not implement user authentication or multi-user access controls.
