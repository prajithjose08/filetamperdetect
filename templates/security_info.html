Security Information

Understanding file integrity, SHA-256, and the limitations of hash-based verification.

What is File Integrity?

File integrity means that a file's contents have not been altered from a known-good state. A file can be tampered with deliberately (by an attacker), accidentally (disk corruption, failed transfer), or unintentionally (software auto-update changing a config file). Detecting tampering early is fundamental to cybersecurity and data assurance.

How SHA-256 Works

SHA-256 (Secure Hash Algorithm, 256-bit output) is a one-way cryptographic hash function. It takes any input — a text file, a photo, a compiled program — and produces a fixed-length 64-character hexadecimal string called a digest or hash.

Input: Hello, World!

SHA-256: dffd6021bb2bd5b0af676290809ec3a5 3191dd81c7f70a4b28688a362182986d

Input: Hello, World.  (period instead of exclamation mark)

SHA-256: f4d8b2c3a1ee5b0e6ff5b49e789e2f63 a09d48c32dda9bbf9c2e7b3c1e5fa40d

One character change → completely different hash. This property is called the avalanche effect.

SHA-256 is a core building block in TLS/HTTPS, digital certificates, code signing, and software distribution integrity checks (e.g., Linux ISO checksums).

Why a Single Byte Change Matters

SHA-256 was designed so that even the tiniest change causes an entirely different output. This makes it impossible to modify a file without the hash changing — and therefore impossible for tampering to go undetected, as long as the original hash is trusted.

What Hash Comparison Can and Cannot Do

  • Can detect: Any change in file content, regardless of how small.
  • Cannot identify: Who made the change, when exactly, or which bytes differ.
  • Cannot prove: That the original file was authentic in the first place — only that it matches the saved reference.
  • Cannot resist: An attacker who also has write access to the database — they could update the stored hash to match the modified file.

Why the Reference Hash Must Be Protected

The integrity check is only as trustworthy as the stored reference hash. If an attacker can modify the database, they can replace the reference hash with a new one, making a tampered file appear clean. In production systems this is addressed by:

  • Storing reference hashes in a write-once, append-only log.
  • Using digital signatures (e.g., RSA or ECDSA) so the hash is signed with a private key.
  • Publishing hashes to an immutable ledger or trusted third-party service.
  • Applying OS-level access controls to restrict who can write to the database file.

Limitations of This Application

  • This application stores reference hashes in a local SQLite database file (instance/file_integrity.db). Anyone with write access to that file can alter the stored hashes. This application does not provide a digitally signed or tamper-proof audit trail.
  • SHA-256 is a hash function, not a signature scheme. It proves the file matches its reference but does not prove who registered the reference or when.
  • The application does not identify which specific bytes or lines changed — only whether the overall hash differs.
  • File upload is restricted by extension, but extension checks can be bypassed. This application is intended for local, educational use — not as a production security control.
